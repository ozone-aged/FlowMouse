# Upstream update and release workflow

The user requests ongoing independent improvements based on each new stable Hmily-LCG/FlowMouse release. This is a source copy, not a GitHub fork. Preserve authorship, GPL-3.0 and third-party notices. Never push to upstream. Do not connect this browser extension to app-manager or install it into the user's browser automatically.

No scheduler, daemon, login item or background monitor is installed. Run `npm run upstream:check` to discover a new stable version. New releases require actual review and validation; a new tag alone must never trigger blind redistribution.

1. Read `UPSTREAM.json`, current Git state, release notes and current release metadata. Fetch the latest stable release from GitHub and resolve its tag to a commit. Download its source archive, record its URL, tag, resolved SHA and archive SHA-256. GitHub source archive checksums document the bytes used; they are not an author signature.
2. Import the unmodified source into an isolated branch and tag it `upstream-vX.Y`. Compare with the previous pristine upstream tag before integrating into the improved branch. Preserve local improvements and all upstream features. Do not replace the improved branch blindly with the archive.
3. Review manifest permissions, host access, new dependencies, vendored libraries, remote requests/telemetry, message handlers and their senders, web-accessible resources, URL navigation, downloads, clipboard, unsafe HTML, settings imports and custom CSS. Review new actions and schema changes before adjusting import validation. No new permissions or telemetry without a concrete functional need.
4. Review each local change against the new upstream version. Drop fixes already solved upstream; port the additive navigator, accessibility and settings reliability improvements as needed. Keep gesture execution and defaults intact unless a concrete reviewed issue requires change. Prefer TypeScript for new modules; avoid a wholesale rewrite.
5. Run `npm ci`, `npm run check`, `npm test`, `npm audit --audit-level=moderate`. Build and run `npm run test:browser` in a disposable Chromium profile. Run the browser test on Windows as well when a runner is available. Include valid old/new backups, malformed/prototype-key/oversized backups, storage quota failures, default gestures, popup and settings in both themes, Korean, narrow windows, keyboard and reduced motion. Stop test browsers and delete disposable profiles.
6. Update version and provenance. Use tag `v<upstream>-ozone.<revision>` and a numeric four-component manifest version, e.g. upstream `2.5` + local revision `1` → manifest `2.5.0.1`. For a three-component upstream version, keep all three components and put the local revision fourth. Ensure it is greater than the preceding installed version under Chromium's numeric rules; inspect the previous release rather than assuming.
7. Update `docs/SECURITY-REVIEW.md`, `docs/RELEASE-NOTES.ko.md`, installation filenames, and `UPSTREAM.json`. Run `npm run package`. Extract the ZIP in a fresh directory, load that exact directory for the browser tests using `FLOWMOUSE_EXTENSION_DIR`, and ensure no development files/secrets are shipped. Produce SHA256SUMS for all uploaded assets.
8. Commit and push the independent repository. Create the GitHub release on the verified commit, attach the install ZIP, independent source ZIP and checksums. GitHub also offers automatic source archives, which need `npm ci && npm run build` before loading. Verify the published tag/commit, asset names, remote sizes and downloaded hashes. Never claim Windows/Edge/Firefox runtime testing unless it was actually performed.
9. Keep the working tree clean and test processes stopped. Report the release URL, actual checks, limitations and how Windows users install/update the ZIP. Preserve baseline tags and migration compatibility for subsequent cycles.

## Local development

Node.js 24.21 or newer, npm and Chromium for Playwright are development tools only. End users need no Node.js runtime.

```sh
npm ci
npm run check
npm test
npx playwright install chromium
npm run test:browser
npm run package
npm run upstream:check
```

Tests use synthetic pages and a fresh disposable browser profile; never the real user's bookmarks, history or logged-in sessions. `PLAYWRIGHT_BROWSERS_PATH` may point to a workspace cache. Browser tests close their context in `finally`. Package ZIPs contain compiled TypeScript enhancements, never node_modules. Compiled code is generated by `npm run build` and intentionally not committed.
